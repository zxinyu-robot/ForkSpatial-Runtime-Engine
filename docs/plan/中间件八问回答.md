# 自研中间件：八问回答

按现状如实回答，区分"已有 / 已设计未实现 / 没有"。

## 1. 主要解决什么问题

一句话：机器人在弱网/断网、定位可能失效、地图会切换的真实楼宇里，**如何判断一条任务和一份空间状态"现在还能不能用"，用不了怎么恢复，这段经历怎么留下来下次少犯**。拆成三个具体问题：

- 任务在正确的权限、时间、空间版本、通信条件下执行，结果可追溯（目标 1）；
- 状态不可信时按可信度分级恢复，而不是无差别重试（目标 2）；
- 经历转成可复用、可淘汰的经验（目标 3）。

它**不**解决：SLAM 精度、运动控制、通信传输本身。

## 2. 用什么机制

已实现（PR #7）：统一的身份/版本/代数/坐标系（`AssetRef`）、增量基线校验（`DeltaRef.dispose`）、分级授权的可信度（`LocalizationHealth → Full/Restricted/Suspended/Revoked`）、唯一原因码、代数切换批量失效（TTL 没到也作废）。

已设计待实现（PR #8 及以后）：执行令牌（owner/epoch 栅栏/租约）、启动截止与运行超时分开、幂等去重、Thin Harness 六步准入、上行数据三类（关键事件不可覆盖/最新值可丢/大块续传）、恢复结果验证、Token 带来源与验证状态、经验先候选经旁路比对再晋升。

机制的共同点：**所有判断都是契约里的纯函数**（`admit / dispose`），准入和运行期复用同一份，不让 BT 节点各写一套。

## 3. 边、端两头接口能否对齐

能对齐，但目前只对齐了"字段"，没对齐"运行"。

- 端侧：Go2 的 `NavigationContextState`（generation/floor/map/session/frame）、`/lio/*` 话题、LNR 的 `RecoveryState` 到契约的映射表已写在 `docs/contracts/spatial_state.md`；适配器（C 阶段）未写。
- 边侧：DJI 物模型三要素 → Asset/Health/State、Intent/Query/Configure、Feedback/环境事件/安全事件的映射已定；`intent.v1` 九字段已定；JSON schema 和 IDL 生成未做。
- 风险点一个：`localization_epoch` 与 `generation` 是否分开还没定，它决定端侧 SHM 页要不要加字段。

## 4. 与成熟具身 OS/中间件的差异化与壁垒

先说实话：**"Runtime + Harness + 记忆"这个架构已经不是壁垒**，ABot-AgentOS、HoloAgent-0 都有；ROS 2/DDS、Nav2、MoveIt 覆盖了通信、导航恢复、操作规划。我们不替代它们。

差异化在三处别人没做或没做实的地方：

- **空间状态的"可用性语义"**：revision≠作废、generation=作废、localization_epoch 只作废位姿锚定、增量基线不符不应用——现有 OS 只有 TTL 和时间戳，没有这套代数/基线规则；
- **可信度驱动的分级授权 + 恢复后验证**，而不是置信分数或重试次数；
- **断网仍自主**：契约默认链路不可靠，运行时不依赖远端作为安全闭环的一部分；

真正的壁垒不是代码，是**真机数据与基线数字**：在真实楼宇跨楼层场景下，证明这套语义比"TTL + 重试 N 次"降低了错误经验复用率和恢复时间。这个目前为零，是 C/E 阶段要补的。

## 5. 性能是否支持长期稳定

**目前没有证据。** 已有的只是 4 个单元测试、毫秒级跑完。长期稳定需要但尚无：长时间运行的内存增长曲线（TokenStore 淘汰、经验库上限）、DDS/SHM 压测（时延 P99、抖动、分配）、断链/重连循环的一致性、真机 MTBF。路线 M6/M7 列了这些指标，没一个有数字。诚实的说法：架构上为长期运行留了位置（代数失效、增量续传、本地日志），但"稳定"要靠 F 阶段压测和真机长跑证明。

## 6. 是否具备 LTS 生命周期维护

**不具备。** 现状：无版本号策略、无弃用流程、无兼容性承诺、无发布节奏。契约层已经预留了 `schema_version`、`vocab_version`、`codec_id`，这是 LTS 的前提，但只是字段。要做 LTS 至少需要：契约语义化版本 + 变更需同时更新映射表与测试、IDL 向后兼容规则、每个 LTS 版本固定一组真机回放数据作回归基线、冻结期。这些都在 F 阶段之后，现在不该承诺。

## 7. 是否有系统级维护措施

部分有雏形：原因码统一（可审计）、证据链字段（可追溯）、fragment log（断网事实源）、CI 双平台。缺：健康监控与告警、故障注入框架（PR #7 的九项用例是起点，没有自动化注入）、配置/策略版本回滚的运维入口、日志与回放工具链、安全更新机制。建议把"故障注入 + 回放回归"作为 B/C 阶段的硬要求，否则后面每加一个插件都回不去。

## 8. 与未来"空间群治操作系统 / 参与社会治理"方向的关系

这套契约天然是多主体的：`robot_id/session_id/owner_id/epoch` 已经为多执行者、多控制方预留；Spatial Asset/Delta 是跨设备共享空间状态的基础；执行令牌/租约是多机争用（通道、电梯、工位）的协商原语；分级授权与可否决是把"谁有权让机器人动"写进协议。往群体/治理方向延伸时会多出三类问题，现有设计都还没碰：**空间资源的所有权与仲裁**（谁拥有一个区域/一部电梯的使用权）、**跨组织的信任与审计**（证据链要能跨机构验证，不只是本机日志）、**人与规则的接入**（治理规则作为约束下发，机器人只在约束内自治）。我的建议是现在不为这个方向加任何代码，只做一件事：契约里凡是标识符都带 owner/scope，凡是决策都带原因码和依据版本——这两条守住，H 阶段之后往群治扩时不用推翻。

## 综上

问题定义清楚、机制有一半落地、接口对齐了字段没对齐运行；差异化成立但壁垒要靠真机数据；性能、LTS、系统维护三项目前都没有，且不应现在承诺；群治方向只需守住两条契约纪律。最该补的次序：C 阶段真机旁路数据 → 故障注入与回放 → 压测 → 再谈 LTS。
