# 契约对齐：第一步从哪开始（历史记录）

> 本文记录 2026-10-24 "从哪开始"的判断过程与依据。当前以《完整技术路线》为准：阶段 A = PR #7 已完成，
> 后续范围见其 §6。本文 §3/§5 中与现状不符处已标注。

> 依据：2026-10-24 三个仓库 main 分支源码与文档（MotionSLAM_ws / fork-spatial-runtime / legged-navigation-runtime），以及你给的 ChatGPT「Runtime + Harness + 可插拔策略记忆」思路。

## 0. 一句话结论

**第一步不是搭 DDS/SHM 中间件，也不是把三个仓库的状态机合并，而是先定义一个所有仓库都缺的东西：`空间状态可信度（SpatialStateCredibility）+ 统一版本链 + 统一原因码`。**
落点在 `fork-spatial-runtime`，一个 PR，不碰冻结的 ROS overlay。理由见 §2。

你的 4 个目标里，这个契约是唯一的公共输入：
- 目标 1「可信度驱动任务恢复」——没有可信度定义就没有恢复触发条件；
- 目标 2 Token 的 `confidence`、ESN 的 `LocalizationReset/FloorChange` 重置——目前是凭空填的；
- 目标 3 世界状态——它的最小单元就是「带可信度和版本的空间状态」；
- 中间件——DDS/SHM 只是搬运，先得有搬什么的 schema。

## 1. 现状：三个仓库在"同一件事"上各说各话

我把源码里真实存在的字段抓出来对照（不是文档愿景）：

### 1.1 时间
| 仓库 | 实际 | 
|---|---|
| fork-spatial-runtime | `Timestamp = int64 ns`（model.h） |
| legged-navigation-runtime | `timestamp_ms int64`（relocalization_supervisor.h） |
| MotionSLAM_ws | 反馈 JSON `timestamp_ns`；信封 `timestamp` **ns 或 ms 二选一**（>1e15 判定） |

→ 单位不统一，也没有人声明是 monotonic 还是 wall clock。弱网/断网下重连后对时，这个坑一定会踩。

### 1.2 身份与版本链（最乱的一处）
同一类概念在三个仓库里有 **6 个名字**：

| 概念 | MotionSLAM_ws | fork-spatial-runtime | task_runtime(MotionSLAM) |
|---|---|---|---|
| 机器人/会话 | `session_id`(string) + `session_token`(u64, SHM 页) | `robot_id`(u32) + `session_id`(u32) | — |
| 资产身份 | `floor_id` + `map_id` + `tile_id` | `asset_id`(string) | `asset_id` |
| 资产内容版本 | `map_version`(u64) / `layer_version` | `revision` | `revision` |
| 有效期代数 | `context_generation` / SHM `generation` | （无，只有 Token `ttl_ns`） | `context_generation` |
| 执行版本 | `traj_id`(MotionCommand.msg) | `subgoal_index` | `current_skill_index` |
| 坐标系 | 默认 `world` | `Subgoal.frame_id` 默认 **`"map"`** | `frame_id` |

→ `revision`（内容变了）和 `generation`（旧状态作废）是两个语义，FSR 现在只有前者；`frame_id` 默认值 Go2 侧是 `world`、FSR 侧是 `map`，直接对接会错。

### 1.3 定位可信度（目标 1 的核心，目前没有任何一处定义完整）
| 仓库 | 表达方式 |
|---|---|
| MotionSLAM_ws 实现 | 散落在话题：`/lio/backend/pgo_state`、`/lio/backend/drift_estimate`、`/lio/relocation/converged`、`/lio/relocation/fitness`、`/local_map/stance_ok`、`navigation_context/ready` |
| MotionSLAM_ws 文档 | `NORMAL_3D → DEGRADED_2D → RELOCALIZING → VERIFYING → RESTORED / HOLD`（规划 §6，未实现） |
| task_runtime | `SafetyMode{Normal, Degraded, Hold}` |
| fork-spatial-runtime | `RobotState{localization_valid: bool, localization_jump: bool}`；`GeometricObservation.localization_quality [0,1]` |
| legged-navigation-runtime | `LocalizationObservation{tracking_valid, pose_jump_m, alignment_fitness}` + `RecoveryState{Tracking, Searching, Aligning, Verifying, SafeStop}` |

→ 五种表达，没有一个同时回答「现在多可信 / 为什么 / 还允许做什么」。而这恰恰就是"可信度驱动任务恢复"要的那个字段。

### 1.4 失败原因码
| 仓库 | 原因码 |
|---|---|
| MotionSLAM_ws 信封 | `plan_fail / stuck / glass_trap / link_lost`（4 个字符串） |
| MotionSLAM_ws 编排器事件名 | `plan_fail_hold / escape_* / drift_icp_* / pgo_applied_redispatch / mission_failed ...`（≈20 个字符串，无枚举） |
| fork-spatial-runtime | `FailureCode{ReplanTimeout, Stuck, PlanFailedRepeated, LocalizationLost, NoWaypoints, Canceled}`；但 `DecisionOutcome.failure_code` 又是 **string** |
| legged-navigation-runtime | 无原因码，只有状态 |

→ 目标 2「执行反馈回流 ESN/策略」要的 `failure_code` 现在在 FSR 内部就两套类型。

### 1.5 生命周期：三层状态机其实是嵌套关系，但没人写明
```
TaskRuntime.TaskStatus      Accepted/Running/Paused/Holding/Succeeded/Failed/Canceled   （任务，MotionSLAM runtime/）
  └ MissionOrchestrator      Idle/WaitReady/Running/Recovering/Succeeded/Failed/Canceled （子目标推进，FSR src/mission）
       └ RecoverySupervisor  Tracking/Searching/Aligning/Verifying/SafeStop              （定位恢复，LNR）
```
外加 Go2 侧还有 `ExecPhase`、`mode_state INIT/ARMED/ACTIVE/EXCEPTION/TERMINATED`、`/demo/lifecycle/state` 三套。
→ 不需要合并成一个，但要**写死包含关系与升级/降级规则**（例如 SafeStop 必然把 Mission 推到 Recovering、把 Task 推到 Holding）。

### 1.6 跨楼层 / 换图：契约空白
Go2 侧已有 `NavigationContextState`（SHM 页：`floor_id/map_id/map_version/session_token/tile_token/generation/relocation_converged/ready`），这是你跨楼层切换真正依赖的数据结构。FSR 侧只有 ESN 的 `FloorChange` 重置原因码。
→ 「楼层切换 = 资产切换 + generation 递增 + 重定位验证通过后才恢复任务」这条规则目前只存在于代码行为里，没有契约。

## 2. 为什么从「可信度 + 版本链 + 原因码」开始，而不是别的

| 备选起点 | 为什么不先做 |
|---|---|
| 先搭 DDS/SHM/UDP 数据分发 | 传输层要承载的 IDL 就是上面这些字段；字段没定，IDL 一周后就得重写。 |
| 先统一三套任务状态机 | 它们是嵌套关系不是重复；真正缺的是三层之间传递的那个"可信度"字段。 |
| 先做 Token/ESN 对接 Go2 | `SemanticToken.confidence`、`ESN reset` 的输入都是可信度；没有它 Token 层就是假数据。 |
| 先改 MotionSLAM_ws | overlay 冻结；而且 Go2 侧真实信号已经够用，缺的是接收方的定义。 |

ChatGPT 那篇的核心是 **Task Contract / Skill Contract / Memory Contract 三契约 + Runtime 掌握执行授权**。对照你的仓库：
- Task Contract ≈ `TaskIntent`（已有，MotionSLAM runtime/task_runtime）
- Skill Contract ≈ `MissionRequest/MissionCommand`（已有，FSR src/mission）
- Memory Contract ≈ `SemanticToken`（**半有**：有 `status/ttl/confidence`，缺 `verification_status / preconditions / invalidation_conditions`）
三个契约之间缺的公共字段就是「状态可信度 + 版本」——它决定 Runtime 什么时候收回执行授权。所以第一步做它，和那篇思路是一致的。

## 3. 第一个 PR 具体做什么（fork-spatial-runtime）

> 已被"附：修正后的 PR #7 内容"与《完整技术路线》§6 的 PR #7 实际内容取代；本节保留作对比。

**新增 `src/contract/spatial_state.h` + `docs/contracts/spatial_state.md`**，零第三方依赖，和现有风格一致。内容只有四块：

```cpp
namespace fork_spatial::contract {

// 1) 统一身份与版本链（给每个仓库一张映射表，不改它们现有字段名）
struct AssetRef {              // ← MotionSLAM floor_id/map_id/tile_id/map_version ; task_runtime world_reference
  std::string asset_id;        //   建议编码 "building/floor/map/tile"
  std::uint64_t revision;      //   内容版本（= map_version / layer_version）
  std::uint64_t generation;    //   有效期代数（= context_generation / SHM generation）；变了即旧状态作废
  std::string frame_id;        //   必填，无默认值（避免 world/map 歧义）
};

// 2) 时间：统一 ns，显式声明时钟域
struct Stamp { std::int64_t stamp_ns; std::int64_t valid_until_ns; ClockDomain clock; };

// 3) 空间状态可信度：合并 规划§6 / task_runtime.SafetyMode / LNR Observation / Go2 话题
enum class LocalizationMode { Normal3D, Degraded2D, Relocalizing, Verifying, Hold };
struct LocalizationHealth {
  LocalizationMode mode;
  double quality;              // [0,1]，喂 Token.confidence / GeometricObservation.localization_quality
  double pose_jump_m;          // ← LNR pose_jump_m / Go2 drift_estimate
  double alignment_fitness;    // ← LNR / Go2 /lio/relocation/fitness
  std::uint32_t healthy_frames;// ← LNR healthy_frames_to_resume
  bool stance_ok;              // ← Go2 /local_map/stance_ok
  ReasonCode reason;
};
// 授权规则（写进契约文档）：Normal3D=全权；Degraded2D=限速限域；Relocalizing/Verifying=StopTrajectory 保持任务；Hold=收回授权→Task.Holding

// 4) 统一原因码：一个 enum + 稳定字符串名，替换 FailureCode(enum) 与 failure_code(string) 两套
enum class ReasonCode { None, PlanFailed, ReplanTimeout, Stuck, LocalizationLost, LocalizationJump,
                        RelocalizationTimeout, FloorTransition, AssetStale, LinkLost, SafetyVeto, Canceled };
}
```

同一个 PR 里顺手做三件最小改动，让契约立刻"有人用"：
1. `MissionOrchestrator::RobotState` 的 `localization_valid/localization_jump` 两个 bool → 换成 `LocalizationHealth`（保留旧字段做过渡 getter）。
2. `mission::FailureCode` 与 `DecisionOutcome.failure_code` 统一到 `ReasonCode`。
3. `docs/contracts/spatial_state.md` 末尾放 **Go2 映射表**：每个字段 ← 哪个话题/SHM 字段，这是后面写 Go2 适配器的唯一依据（overlay 不动）。

验收：`ctest` 现有 3 个 example 测试继续过 + 新增 `test_contract.cpp`（Hold 必触发 StopTrajectory；generation 变化必拒旧 subgoal；frame_id 为空必拒收）。

## 附：通读 ChatGPT 分享后的修正（2026-10-24）

分享的最后一段（"现在工程在和 MotionSLAM_ws 进行契约对齐"）才是和本任务直接相关的部分，它对上文有三处修正、两处确认：

### 修正 1：第一个 PR 的接入点不是 MissionOrchestrator，而是认知层
分享明确：**MotionSLAM 的 BT / 规划器 / 闭环 / 安全监督决定运动怎么执行；FSR 只产出"状态证据 + 策略建议"，不再做一套任务编排器**，并警告"不要出现两个互相覆盖的策略管理器"。
上文 §3 把 `LocalizationHealth` 深度接入 `MissionOrchestrator::RobotState` 的方案，实际上是在加固一个与 Go2 BT 重复的编排器。改为：
- `MissionOrchestrator`：只把 `FailureCode` 换成统一 `ReasonCode`（别名），定位为**参考执行器 / 测试夹具**，不再扩功能；
- 真正接入 `contract::` 的是认知层三件事：
  1. `TokenStore` 增加按 `AssetRef.generation / session_id` 批量失效（定位重置后 TTL 未到的 Token 也必须作废——分享原话）；
  2. `PolicyDecision` 补齐分享要求的字段：`task_id`、策略版本（已有）、引用的空间上下文 `AssetRef`、适用条件、有效期 `Stamp`、拒绝/降级原因 `ReasonCode`；
  3. `DecisionOutcome` 补齐：`ReasonCode`、实际执行的策略版本、相关空间状态版本 `AssetRef`——这是"每次决策都有证据链"的最小字段。

### 修正 2：MotionSLAM 派生状态走"空间观测适配器"，不走因子图事务接口
分享指出 FSR 有两层定位（`architecture.md` 的因子图事务内核 vs README 的 Token/ESN/EdgePolicy 认知闭环）。Go2 的位姿/地图/Frontier 是**派生状态**，应通过 `GeometricObservation` 一侧的适配器进入认知层；只有需要增量因子/优化事务的地方才碰 `SpatialRuntime`。上文 §4 的 C 步（Go2 adapter）据此落在认知层入口，不碰状态内核。

### 修正 3：先旁路运行，再进决策路径
分享的推进顺序：锁一条端到端数据链 → **旁路运行（只算只记，不改变导航行为）** → 验证失效与反馈 → 量化基线。上文 §4 的 C/D 步之间插入"旁路模式"门槛：Runtime 的建议只记录到 fragment log，与 Go2 BT 实际决策并排比对，正确率达标后再允许进入受限行为选择。

### 确认 1：字段取舍
分享列的四个不可互替字段 `revision / context_generation / session_id / frame_id`，与上文 `AssetRef` 完全一致；"稳定的失败类型"对应统一 `ReasonCode`。`glass_trap` 按 `SafetyVeto + detail` 归类，与分享"安全否决"作为独立反馈类型一致。

### 确认 2：失效测试清单（直接作为 PR #7 验收）
分享点名至少测：定位重置、跨楼层、过期 Token、地图版本不一致、规划失败、安全否决、执行超时——每种都要验证 Runtime 停止使用旧证据。PR #7 的 `test_contract.cpp` 按这七项写用例，替代上文 §3 的三条验收点。

### 不采纳的部分
分享前半段的 README 重定位、`IPolicyMemory` 抽象、策略晋升协议、家电维修/VLA/WAM 对比，属于 FSR 第 1/3/4 阶段和论文选题，不在本次契约对齐的关键路径上；分享自己也说"既然正在推进契约对齐，就不应急着重新定义项目定位"。
